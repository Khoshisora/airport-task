# Task 3. Multithreading — Аэропорт

Проект к заданию **Java. Task 3. Multithreading** (Innowise, 2026), индивидуальный
вариант 3 — **Аэропорт**.

Самолёты прилетают в аэропорт, занимают гейты, высаживают и принимают пассажиров.
Каждый гейт обслуживает только один самолёт, количество пассажиров не может превышать
вместимость самолёта или терминала, каждый самолёт обязательно должен быть обслужен.

## Формат данных

Первая содержательная строка — аэропорт, каждая следующая — рейс. Пустые строки и
строки, начинающиеся с `#`, игнорируются.

```
# имя | гейтов | вместимость терминала | пассажиров уже в терминале
Sheremetyevo | 3 | 240 | 100

# рейс | вместимость самолёта | пассажиров на борту (высадка) | пассажиров на посадку | время обслуживания, мс
SU-100 | 180 | 0 | 60 | 700
SU-200 | 160 | 80 | 0 | 600
```

Правила чтения и валидации:

* файл читается в UTF-8, ошибки содержат номер строки и имя источника;
* `boarding ≤ capacity` и `onboard ≤ capacity` — количество пассажиров на борту
  самолёта не превышает его вместимость (все пассажиры «на борту» высаживаются, затем
  самолёт принимает пассажиров на посадку);
* `0 ≤ initial passengers ≤ terminal capacity`;
* идентификаторы рейсов уникальны, гейтов и рейсов должно быть хотя бы по одному.

### Потоки

Каждый самолёт — это `Plane implements Callable<PlaneReport>`. `AirportService` создаёт
`ExecutorService` с числом потоков, равным числу рейсов, и отправляет каждый самолёт
отдельной задачей:

```java
List<Future<PlaneReport>> futures = executor.invokeAll(planes);
for (Future<PlaneReport> future : futures) {
    reports.add(future.get());
}
```

Пул такого размера нужен, чтобы все самолёты могли одновременно стоять в очередях за
терминалом и гейтами; при меньшем пуле часть самолётов вообще не начала бы работу, пока
другие ждут освобождения ресурсов. Имена потоков — `plane-worker-N`.

После обслуживания пул корректно завершается: `shutdown()`, ожидание через
`awaitTermination(..., TimeUnit.SECONDS)`, при необходимости `shutdownNow()`.

### Терминал: резервирование вместо «захвата и ожидания»

`Terminal` использует честный `ReentrantLock` и `Condition`. Плоскость не может просто
«занять место и ждать»: это привело бы к взаимной блокировке, когда все гейты заняты
самолётами, ожидающими места в терминале. Вместо этого самолёт **атомарно резервирует**
и высадку, и посадку:

```java
passengers + reservedIncoming + disembarking <= capacity   // хватит места
passengers - reservedOutgoing >= boarding                  // хватит пассажиров
```

Если условия не выполнены, поток ждёт на `Condition` и освобождает блокировку. После
успешного резервирования самолёт уже гарантированно сможет завершить обмен без
дополнительного ожидания.

Инварианты (проверяются после каждого изменения):

* `passengers + reservedIncoming ≤ capacity` — терминал не переполнится;
* `passengers ≥ reservedOutgoing` — обещанные пассажиры всегда есть в наличии.

Порядок получения ресурсов: **сначала терминал, потом гейт**. Самолёт никогда не держит
гейт в ожидании терминала; владелец гейта всегда может завершить уже
зарезервированный обмен. Поэтому цикл ожидания невозможен: гейт освобождается, и
ожидающие самолёты продолжают работу.

### Пул гейтов

`GatePool` хранит свободные гейты в очереди, защищённой честным `ReentrantLock`.
`acquire()` ждёт на `Condition`, пока все гейты заняты; `release()` возвращает гейт в
очередь и будит ожидающего. Один гейт не может быть выдан двум самолётам: занятие и
освобождение выполняются под блокировкой пула.

### State-машина самолёта

Состояний больше двух, поэтому используется State. Каждое состояние — отдельный класс
без изменяемого состояния; `Plane#call()` просто крутит цикл до финального состояния:

```
ARRIVING → AWAITING_TERMINAL → AWAITING_GATE → DISEMBARKING → BOARDING → DEPARTING → DEPARTED
```

| Состояние | Действие |
|---|---|
| `ArrivingState` | регистрирует заявку на обслуживание |
| `AwaitingTerminalState` | резервирует место и пассажиров в терминале |
| `AwaitingGateState` | получает свободный гейт |
| `DisembarkingState` | имитирует высадку и применяет её к терминалу |
| `BoardingState` | имитирует посадку и применяет её к терминалу |
| `DepartingState` | освобождает гейт |
| `DepartedState` | финальное состояние |

Задержка обслуживания задаётся в файле и выдерживается через
`TimeUnit.MILLISECONDS.sleep(...)` отдельно для высадки и посадки (если операция не
нужна, задержки нет).

### Singleton аэропорта

`Airport` создаётся лениво и потокобезопасно:

```java
private static final ReentrantLock INSTANCE_LOCK = new ReentrantLock();
private static Airport instance;

public static Airport getInstance(AirportConfig config) {
    INSTANCE_LOCK.lock();
    try {
        if (instance == null) {
            instance = new Airport(new AirportFacilities(...));
        }
        return instance;
    } finally {
        INSTANCE_LOCK.unlock();
    }
}
```

Поле `instance` читается и записывается только под замком, поэтому `volatile` не нужен.
`enum` и статический внутренний класс (решение Билла Пью) не используются. Сами ресурсы
аэропорта вынесены в `AirportFacilities`, что позволяет тестировать их без глобального
состояния.

## Решения, которые стоит уметь объяснить

* **Почему резервирование, а не `BlockingQueue`.** Очередь пассажиров не позволяет
  атомарно проверить и вместимость, и наличие пассажиров для посадки, а также не даёт
  гарантий завершения при занятых гейтах. Резервирование под одним замком решает обе
  задачи и не нарушает запрет на `BlockingQueue`.
* **Почему терминал берётся раньше гейта.** Если сначала занять гейт и ждать места в
  терминале, все гейты могут оказаться заняты ожидающими — возникнет взаимная
  блокировка. При обратном порядке владелец гейта всегда завершает обмен.
* **Почему `Callable`, а не наследование от `Thread`.** Каждый самолёт всё равно
  исполняется отдельным потоком пула, но `Callable` возвращает отчёт и позволяет
  дождаться результата через `Future`. Это же прямо разрешено заданием.
* **Почему `ReentrantLock` вместо `synchronized`.** Задание запрещает `synchronized`;
  кроме того, нужны честная очередь и `Condition` для ожидания без активного цикла.
* **Почему State.** У самолёта семь состояний и переходы зависят от текущего шага;
  отдельные классы убирают `switch` и делают переходы явными.
* **Почему Singleton на замке.** Ленивая инициализация без `volatile` и без
  double-checked locking: все обращения к полю выполняются под одним замком.
* **Почему `main` печатает отчёт.** Задание разрешает использовать `main` для вывода
  работы потоков; логи при этом остаются в Log4j2.

## Ограничения

* Данные считаются корректными (по условию задания). Если все рейсы только высаживают
  пассажиров и терминал заполнен, обслуживание невозможно в принципе — это следствие
  ограничения вместимости, а не ошибки синхронизации.
* Пассажиры на посадку должны уже находиться в терминале (начальный пул в файле или
  пассажиры, высаженные другими рейсами). Самолёт резервирует посадку до собственной
  высадки, поэтому не может посадить пассажиров, которых сам только что высадил.
* Число потоков равно числу рейсов; файл рассчитан на небольшое количество самолётов.
* Прерывание потока самолёта завершает рейс с `AirportException`; штатный сценарий
  предполагает обслуживание без прерываний.
* Время обслуживания имитируется задержкой из файла; реальные операции с пассажирами не
  моделируются.
